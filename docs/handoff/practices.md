13. **门禁/折算的数据面必须按实体类型分派，不能硬编码单一实体的数据源**：2026-08-15 M3-c 复审（D-039）——SPREAD_DRIFT 二次门禁数据面按 spec §10.3 硬编码 `LatestFacts(ticker)` + `LatestFacts(funding)` 双查（这是 funding_hedge 语义），导致 repo（无 ticker，面值锚 100）、carry（无 funding，稳定币生息）两类订单**确认恒拒**——门禁不是"从严"，是功能残缺。修法：按 kind 分派**权威数据源**（repo→reverse_repo 利率、carry→defi_rate 年化、funding_hedge→ticker/funding），fail-closed 语义保持（每类权威源查不到仍拒）。模式：任何"阈值/门禁/折算"若服务多类实体，先枚举**每类实体的数据源**再写数据面；"一类实体的数据面天然通用" = 隐蔽的假设坑。与 #11 同源（验证目标与方法匹配），区别在 #11 是统计工具，本条是数据面映射。

14. **跨数据源同名数值字段口径不同，必须按 source/来源标注口径，不假设语义一致**：2026-08-16 D-040（SimExec 测试网账户区）——`equity_usd` 同名，OKX 给 `totalEq`（交易所精确折算），binance `fapi/v2/balance` 不给 USD 值，只能做稳定币（USDT/USDC/BUSD/FDUSD）合计**近似**（非稳定币无行情折算）。把两路都当"账户权益"展示 = 误导（binance 会低估）。落地：store 类型注释标口径 + 前端按 source 明示「精确 / 近似·非全量净值」+ 无折算资产标 —。任何聚合展示只要跨数据源，先问"这两个同名数字的语义/精确度是否相同"再决定是否并排。

15. **SQL 动态 WHERE 拼接，每个子句必须加括号**：2026-08-16 D-042 演练单拒单根因——`where := []string{"$1 = '' OR kind = $1", "$2 = '' OR venue = $2", "$3 = '' OR symbol = $3"}` 用 `AND` join 但各子句缺括号 → 求值 `$1='' OR kind=$1 AND $2='' OR ...`，`AND` 优先级高于 `OR` → 多参数组合退化为「只生效符号条件」：`LatestFacts(ticker, okx, BTC)` 返回 funding+iv+ticker 五行、首行 funding@binance 负值 → `fundingHedgeSignal` 取 `fs[0]` 拿负值当 ticker 价 → UNHEDGED 拒单。修法：每子句自括 `($1='' OR kind=$1)`。教训：**任何 `strings.Join(cond, " AND ")` 的动态 WHERE，条件内一旦含 OR 必须子句自括**；且测试必须覆盖多参数组合（仅空参/单 kind 测不出）。对抗锚点：TestLatestFactsFilters（删括号必红）。

16. **/proc/PID/exe 与磁盘文件对比必须用 `stat -L`（跟随符号链接）**：2026-08-16 D-042 排查曾误判「运行旧二进制」——`stat -c '%i' /proc/PID/exe`（不带 `-L`）返回的是 procfs 为魔法符号链接分配的**伪 inode**，与磁盘文件 inode 必然不同，被误读为"运行进程加载了已替换的旧二进制"，一度把调查引向反汇编/二进制比对错误方向。真相：`/proc/PID/exe` 是符号链接，跟到目标才是文件真身——**对比运行二进制与磁盘须 `stat -L`，或 `readlink /proc/PID/exe` 看是否 `(deleted)`**。教训：procfs 魔法文件（exe/maps/fd）默认 stat 语义特殊，涉及"运行的是什么文件"一律先跟符号链接再下结论。

17. **"二次点击确认"防误点按钮：`disabled` 不能绑 `pending` 态**：2026-08-16 SimExec 确认按钮 bug——首次点击 `setPending(id)` 进入待确认态，按钮文字变"再次点击确认？"，但同时 `disabled={pending === o.id}` 变 true → 按钮被禁用 → **第二次点击永远触发不了 `onClick`**，确认动作悬死（用户"点击无响应"）。修法：`disabled` 绑 `busy`（确认请求进行中防连点），`pending` 态保持可点（正是等第二次点击）。模式：任何"状态 A → 提示再点 → 状态 B"的两段式交互，第一段的显式状态**不能同时是禁用条件**；禁用只绑"正在处理"（busy/pending 请求），不绑"等待用户下一次输入"。

18. **前端展示枚举值（risk_flags 等）必须对照后端常量全集逐一映射，别只映射见过的**：2026-08-16 SimExec 三处修复——`riskLabel()` 只映射了 2/7 个 Risk 常量（SPREAD_DRIFT/WHITELIST），UNHEDGED 等显示英文原文（业主反馈"英文硬编码"）。后端 `internal/sim/order.go` 有 7 个 Risk* 常量，前端映射表漏了 5 个——**枚举值从后端新增到前端展示，缺联动就是无声回退原文**。修法：映射表逐条对照后端常量全集（UNHEDGED→未对冲 / SPREAD_LOW→价差过低 / SIZE_OVER→单笔超限 / DAILY_OVER→日额超限 / INVALID_INPUT→输入无效），未知名回退原名（演进预留）。模式：任何「后端/DB 枚举值 → 前端文案」的映射表，改后端枚举时必须同步核对前端映射全集（可 grep 断言两端常量集一致）；只映射"见过的值"= 隐藏缺口。与 #14 同源（数据面与展示面口径对齐），区别在 #14 是跨源数值语义、本条是枚举文案全集。

19. **交付自审（§7.3 A–F）之后仍有必须操作的事项：部署应用 + 推送远端，不能停在「自审通过 + 本地 commit」**：2026-08-16 确认下单面板重构 + 三处修复收尾——完成自审、STATE/dialogue/practices 落档、本地 commit 后，把「部署应用（构建 → 重启服务让新 bundle 上线）」和「推送 GitHub」当成可选项晾着，等业主主动说"提交，推送，应用"才补上。§7.3 自审只覆盖代码/文档质量，**不是交付终点**；涉及运行态的改动，业主期望的闭环是「改完 → 构建 → 部署应用 → 推送远端」，中间缺一步 = 交付未完成。修法：check-out 收尾清单显式列入这三步（构建/部署/推送），本地 commit 不代表上线；与"应用面验证完成"分别检查。模式：**自审 → 构建 → 部署应用 → 推送** 是完整交付链；"我审过了、提交了" ≠ "交付了"——运行态改动缺部署/推送，等于给业主留了个没上线的半成品。

20. **洞察/建议类引擎 = 只读证据表面，永不自动改规则**：2026-08-16 D-044 进化建议引擎 L0——业主想要"更智能化"，第一反应是"系统帮我调阈值/自执行"，但规则引擎是人工决策的落点（D-019 不赌 / D-043 不接 LLM），任何自动改规则 = 把决策权交给代码 = 违背项目定位。落地：引擎产出「待核实证据候选」（reject_dist/defi_anomaly/no_order/source_down），每条 insight 的 `actions` 一律写成「核实/评估 → 走 D# 人工决策」，**不落任何自动执行路径**；异常检测用截面中位数×因子（regime shift 稳健），纯函数 + 对抗测试。模式：**任何"系统自我优化/自我进化"的提案，先守住边界——优化方向由数据提示、优化动作由决策层拍板**；"证据面"与"执行面"分离，"系统主动出结论"与"系统自动改规则"是两回事，前者是增强、后者是越权。

21. **施工前必须先对设计文档做 A–F 自审（自行施工/分发施工都须）**：2026-08-16 D-045 计划退出前被业主两次打回——"自我审计没有？""不是给我看，是你应该做的流程，设计文档完成，自行施工/分发施工前都必须自我审计文档。避免完工后审计出错误，又重来。" 教训：第一次只把审计当"给业主看的东西"（计划通过后再补），实为流程缺失——完工后审计出错再返工 = 双重代价（返工 + 信任损耗）。落地：**任何非平凡变更，设计文档完成后先走 AGENTS.md §7.3 A–F 自审，结论逐条写进计划文件，再 ExitPlanMode / 分发施工**；§7.3 已加「两时点强制」条款。模式：**自审是施工前置门禁，不是交付材料**；"我审过了"不该由业主追问才做，且施工前 vs 交付前各做一次。

22. **结算/折算数据面必须按实体 kind 分派；落单 venue/symbol 取事实真实值，勿硬编码**：2026-08-16 D-045 把 carry+repo 接入模拟盘，定位两个潜伏缺口——① `settleOnce` 只查 `fact.KindFunding`（funding_hedge 语义）→ carry/repo 腿"建了仓也永不生息"（D-039 修了确认二次门禁侧，结算侧还漏着）；② repoSignal 落单硬编码 `Symbol:"GC001"/Venue:"domestic"`，而 reverse_repo 事实真实存 `venue=sina/symbol=GC001` → 结算按 (venue,symbol) 查 reverse_repo 永 miss。修法：`settleFactKind(kind)` 单点分派（funding_hedge→funding / carry_asset→defi_rate / repo→reverse_repo）+ `SettleFunding` 带 kind 维（同 (venue,symbol) 不同 kind 互不污染）+ 落单 venue/symbol 用 `fs[0].*` 事实真实值。模式：**「一类实体的数据面/门禁天然通用」= 隐蔽假设坑（practices #13 同源）**——凡服务多类实体的结算/折算/门禁，先枚举每类实体权威数据源再写数据面；且**落单键（venue/symbol）必须来自权威事实**，硬编码 = 下游按真实键查询永 miss。

23. **「算账」与「匹配」是公式不是聪明——写死进系统；经验吸收=人工 D# 落盘、匹配=纯函数、呈现=只读，永不自动吸收**：2026-08-16 D-046 机会实算卡 + 市场结构经验库——业主问「投运后不带你，系统如何自己算账」，直觉是"接入 LLM/更聪明"，但那段算账（瞬时 vs 均值 / 摩擦摊薄保本天数 / 扣摩擦净年化 = 尖峰陷阱）全是确定性公式；业主进一步要「新情况吸收成经验资产自我进化」。落地：**实算卡 = 纯函数写死**（公式 + 三档判定 + 中文模板叙述，D-043 不接 LLM）；**经验库 = 签名纯函数匹配 + 只读呈现**（knowledge_match insight + 浏览 RPC），**吸收 = 人工 D# 落盘（seed 进 git）、验证 = 后续重匹配 + 人工复核 → 新 D# 更新 verdict**，系统永不自动吸收/自动改规则。模式：**任何"让系统更聪明/自我进化"的需求，先拆成「公式（写死）」+「经验（人工吸收、机械匹配、只读呈现）」两半**——公式可对抗测试，经验吸收保决策权（AGENTS.md §0 Claude 最高），系统主动匹配与呈现 = 增强，系统自动吸收改判 = 越权（practices #20 同源）。**NaN 值不可用 0 占位**：NetAnnualized 均值样本不足须显式 `math.NaN()`（0 会被 ratingFor 误读为「净 ≤0 坑」判错档，D-046 实战教训）。

24. **数据 hook 必须随视图生命周期挂载，不能绑 App 根；「刷新」必须覆盖它能刷的全部数据；缺失信号用 presence flag 别用 0 占位**：2026-08-16 D-047 前端第一性原则审计——数据 hook（useSnapshot/useFactsSnapshot/useSim/useKnowledge）绑 App 根生命周期而非视图生命周期，产生三症状：① 非当前 tab 的数据仍 60s 轮询（跨 tab 空转，账本/事实页不可见时也白拉）；② 顶部「刷新」只 reload useSnapshot，同页 ConfirmPanel/KnowledgeBoard 不动（刷新名不副实）；③ useSim 无轮询，8h 结算新单在确认面板是旧数据（新鲜度脱节）。修法：**数据 hook 下沉到展示它的页面组件**（hook 生命周期 = 视图生命周期，切 tab 即卸载、effect cleanup 清 interval），App 根只留驱动全局 chrome 的 hook；页面间需要联动刷新 → 顶部 `refreshKey` 状态递增 + 页面内 hook 依赖它重载（全局刷新 = 根 hook reload + refreshKey 递增）。**0 占位二犯（F4）**：`pnl_rmb===0` 曾被当「汇率缺失」信号（0-as-missing 反模式，practices #7 对 NaN、#23 对 NetAnnualized 同族）→ 真零 PnL 被误标「USD 原值」。修法：响应级 presence flag（`ListSimPositionsResponse.fx_available`，镜像 ListFactsResponse 既有模式），缺失信号用 flag 不用 0 占位。模式：**写数据获取层前先问挂载生命周期——App 根常驻 hook 只留给全局 chrome；页面数据必须随视图挂载/卸载**；「刷新按钮」的覆盖范围必须穷举它该刷的全部数据源（refreshKey 信号是机械可查的联动机制）；任何「0/空/缺省 = 缺失」的推断，换成显式 presence flag（后端响应里加 bool，别在前端猜）。

25. **页面布局由「用户第一眼最需要看到什么」决定，不按组件写码顺序堆叠；裁决先于数据、低频内容折叠**：2026-08-16 D-048 总览页布局重构——总览页原顺序 = 机会数据矩阵 → 告警流 → 确认下单（右列底部）→ 触发器 → 建议 → 经验库，是「按组件功能排」而非「按用户第一眼问题排」。业主指示 UI 第一性原则：**第一眼问题层级决定布局**。对本系统（唯一运营者），第一眼问题降序 = ① 该我行动（待确认订单）② 机会裁决（可抓/打平/坑）③ 系统健康（header）④ 信号流（告警/触发器/建议）⑤ 数据下钻（矩阵）。修法：① 确认下单置顶整宽（该我行动永远第一眼可见，空态保底不消失——保住错误横幅/刷新出口）；② 机会实算卡移面板顶部（裁决先于矩阵），数据块包 Collapse（funding 主矩阵默认展开、低频面折叠）；③ 低频参考面（经验库/全量规则表）折叠，命中（knowledge_match）才默认展开。折叠用原生 `<details>` + 受控 open（Collapse 组件三处复用，零 JS 依赖、无障碍、可 grep），**比自建 state 少 20 行**。模式：**写页面布局前先列「该页用户的第一眼问题」并按重要性排序，再定组件顺序**；「行动/裁决/信号」类必须压在「数据下钻/参考」类之前；低频参考面折叠不丢数据面（均可展开）；布局重构若只是顺序/显隐，纯前端零后端改动（含执行门禁——U 项全程不碰 D-016/MinSpread/白名单）。

26. **布局第 2 课：信息架构（眼睛扫描起点）与操作热区（鼠标顺手高度）是布局的两个独立输入；告警流的第一眼形态是「状态」不是「内容」**：2026-08-16 D-050 总览页布局第 2 版——业主不满意 D-048 直接给精确网格：左上1 数据矩阵（**眼睛扫描起点**，监控数据置顶）、右上1 经验库、右2 确认下单（**鼠标顺手高度 = 操作热区**）、左2 实算卡、左3 建议、右3 触发器；并反转了 D-048「裁决先于数据/确认置顶」子决策（走 D# 留痕）。**告警流第1性原则**：告警 = 系统「有情况报告」，运营者第一眼问题是「有没有 N 条未处置」——**状态问题**，不是逐条内容。故第一眼形态 = 未读数徽标（header 铃铛），时间线 + ack 是拉取式第二需求；网格里整墙告警时间线 = 用内容形态回答状态问题，是反第一性的。模式：① **布局输入分两类**——信息架构（第一眼问题层级，practices #25）与操作 ergonomics（鼠标顺手高度/扫视路径），两者可能冲突，业主拍板优先；**布局迭代业主可反转上一版子决策，必须走 D# 留痕**（决策在环）；② **任何「通知/告警/提示流」先问：第一眼需要状态还是内容？** 状态（有 N 条/未处置）→ 徽标放全局 chrome，内容（时间线/详情）→ 拉取式面板；把内容堆首页 = 反第一性；③ 网格布局用 CSS grid auto-flow（组件顺序即视觉顺序），删组件/换位时顺手删死 CSS（.timeline/.row-col 类案例）与死 props，别留孤儿样式。

27. **CSS grid 的 `1fr` 隐式最小 = `auto` 会撑破视口；媒体查询里的规则特异性必须 ≥ 要压过的基础规则；移动布局必须用真实视口实测（375px）替代推断**：2026-08-16 D-051 移动自适应实测抓到两个真 bug（若只靠视觉/推断看不到）——
① **`grid-template-columns: 1fr` 隐式最小是 `auto`**（等价 `minmax(auto,1fr)`），表格 nowrap 内容（矩阵 min-content 556px）会把轨道撑宽 → 整个网格超视口（实测 375px 视口 docScrollWidth 594）。桌面版用了 `minmax(0,3fr) minmax(0,2fr)` 故无恙；移动折叠兜底写的是裸 `1fr` → 中招。修法：任何想「让内容收缩进容器、超宽走内部滚动」的网格轨道，**必须 `minmax(0,1fr)`**（min 0 才允许轨道小于内容 min-content），`.table-scroll{overflow-x:auto}` 才有意义。
② **媒体查询里的覆盖规则特异性不够时静默失效**：基础 `.ledger-form .ledger-note{grid-column:span 2}` 特异性 (0,2,0)，480px 媒体写 `.ledger-note{grid-column:1 / -1}` (0,1,0)——即使媒体在后、matchMedia 返回 true，特异性先决，note 保持 span 2，在单栏网格上撑出隐式第二列（258+218px，实测 docScrollWidth 511）。修法：媒体块里覆盖同一属性用**与基础规则相同的选择器/特异性**（`.ledger-form .ledger-note`），或直接 `!important`（少用）。
模式：① **grid 轨道只要涉及"可能被表格/长内容撑宽"一律 `minmax(0,1fr)`**（grid 的 min 0 语义与 table 的 auto 行为是常见坑）；② **媒体查询覆盖基础规则时，特异性必须 ≥ 基础规则**——浏览器 cascade 先比特异性再比顺序，媒体在后不等于会赢；③ **移动适配验证 = 真实视口实测**（无头 chromium CDP 取 `docScrollWidth` vs `innerWidth`、`getComputedStyle`、触摸目标 bounding rect），不要只截图/目测——375px 实测把两个"看起来对、实际溢 200px"的 bug 抓出来了；④ 断点对齐既有（600px 主断点与铃铛全屏一致），桌面断点做回归（1280px 双栏 + 按钮不被移动规则污染）。
